ROU-245 / COF-010A

Authentication and access-control scope is now explicit.

The docs now tell the Core API scaffold exactly how Cofrete login, roles, account scoping, service credentials, audit logging, and auth errors should behave.

Decision

What changed

The previous docs had good guardrails, but Core API still had to infer the implementation shape. ROU-245 now pins down the first auth model and the security boundaries for follow-up scaffold work.

Auth boundary

Core API owns app login

Cofrete starts with Core API auth endpoints and Spring Security. A future identity provider can replace credential verification without changing the public auth contract.

Session shape

Short access, revocable refresh

API calls use short-lived bearer access tokens. Refresh sessions must be rotation-capable or server-side records that can be revoked per session.

Official portals

No gov.br credential reuse

Cofrete login remains separate from gov.br, ANTT, RNTRC Digital, Receita Federal, ANP, SUSEP, insurer, DETRAN, SEFAZ, and state systems.

Contracts

The auth API is now concrete.

The updated API contract gives COF-005 enough shape to scaffold controllers, DTOs, token/session behavior, and standard error responses without guessing.

Endpoints

Defined Core API surface

POST /api/auth/register, POST /api/auth/login, POST /api/auth/refresh, POST /api/auth/logout, and GET /api/auth/me now include request/response examples and endpoint rules.

Errors

401 and 403 are separated

Missing, expired, malformed, revoked, or invalid credentials return UNAUTHENTICATED. Valid credentials without the required scope return FORBIDDEN.

Access Model

Roles now have implementation boundaries.

User roles, service roles, and account scoping were expanded so Core API, workers, and client apps can use the same principal semantics. Company mode is documented as a reserved post-MVP path, not an active single-driver MVP capability.

Principal
Allowed scope
Restriction
DRIVER
Own account, profile, trucks, trips, documents, receivables, reserves, and compliance records.
Cannot read or mutate another account or company record.
COMPANY_ADMIN
Reserved for post-MVP company mode and company-account records after a future issue enables that workflow.
Must not be active or assignable during the single-driver MVP.
SUPPORT
Restricted support reads and explicitly allowed support actions.
Must target an account and produce audit entries.
PLATFORM_ADMIN
Operational configuration and elevated support workflows.
Elevated access must be logged and should not bypass account-scoped APIs silently.
SERVICE_FINANCE_WORKER
Finance event consumption and calculation result writes.
No broad document, profile, or admin permissions.
SERVICE_DATA_IMPORTER_WORKER
Imported datasets, import audit records, and freshness status.
Cannot act as a driver or mutate driver-entered finance data.

Security

Audit and credential rules were tightened.

The docs now spell out what must be auditable, what credentials each service should use, and where client auth material belongs.

Audit

Elevated and sensitive actions

Support/admin access, financial changes, document access, compliance changes, auth-sensitive changes, and internal worker writes require audit records.

Infrastructure

Separate service credentials

Core API, finance worker, data importer worker, PostgreSQL, RabbitMQ, and object storage should use distinct least-privilege credentials.

Clients

Storage guidance is explicit

Mobile tokens belong in platform secure storage. Web admin should prefer secure, HTTP-only, SameSite cookies when deployment allows it.
