ROU-253 / COF-013A Reserve Allocation Async Result Persistence

Manually maintained derived summary. Canonical source of truth remains the Markdown docs and service code.

What Changed

  • Core API now records reserve allocation requests as REQUESTED instead of doing reserve math synchronously.
  • Core API publishes reserve.allocation.requested with active reserve rules, money inputs, idempotency metadata, and correlation data.
  • Finance Worker consumes the request, calculates deterministic bucket allocations, and publishes reserve.allocation.completed.
  • Core API consumes the completed event and persists wallet credits and reserve transactions idempotently.

Why It Changed

ROU-217 intentionally duplicated reserve allocation math in Core API so mobile and dashboard work could use durable reserve wallets early. ROU-253 removes that temporary ownership gap and makes Finance Worker the reserve allocation math owner while Core API remains the persistence owner.

Affected Areas

  • core-api/src/main/java/com/cofrete/coreapi/reserve: async request creation, result listener, idempotent result persistence, allocation status changes.
  • finance-worker/src/main/java/com/cofrete/financeworker: event-backed reserve snapshots and completed result publishing.
  • docs/architecture/event-contracts.md: new reserve.allocation.completed contract and enriched request payload.
  • docs/architecture/api-contracts.md: reserve allocation endpoint now returns request status before worker result persistence.
  • docs/architecture/service-boundaries.md, service READMEs, and ADR wording now reflect async ownership.
