Architecture docs explained

Cofrete is a docs-first, multi-service platform.

The architecture folder describes how Cofrete should be built: a mobile-first product, a Core API, asynchronous workers, durable data, documented contracts, and Kubernetes as the intended production runtime.

Architecture in one minute

The repository defines the target shape before the service code is scaffolded.

1
Clients stay thin

Mobile and web call Cofrete APIs. Business math stays in backend/domain code.

2
Core API owns product data

It validates requests, stores primary records, publishes events, and stays internally modular by domain.

3
Workers handle async work

Finance calculations and external data imports run behind RabbitMQ events.

4
Production means Kubernetes

Docker Compose is planned for local development only; production targets the user's cluster.

System Shape

Cofrete is planned as a monorepo with multiple deployable services. The client apps do not fetch official external data directly; server-side services import, normalize, audit, and expose it.

mobile-app Driver onboarding, freight calculator, reserve wallet, compliance center.
web-app Admin, demo, support, and operational dashboards.
core-api Synchronous product APIs, auth, validation, and primary business records.
PostgreSQL Drivers, trips, expenses, reserves, documents, receivables, snapshots, imports.
RabbitMQ Finance recalculation, reserve allocation, and import completion events.
finance-worker Deterministic finance calculations, reserve allocation, safe withdrawal, health scoring.
data-importer-worker ANP diesel imports, toll data imports, future ANTT freight-floor imports.

Current status

These docs describe implementation targets. The repository currently has service folders, README files, AGENTS guidance, architecture docs, runbooks, and validation scripts. Source code, Dockerfiles, package files, migrations, and tests are reserved for service scaffold issues.

  • Contracts are markdown source-of-truth until OpenAPI or shared contract packages exist.
  • Kubernetes values are proposed defaults until real cluster discovery succeeds.
  • Compliance wording must stay advisory and point back to official sources.

Service Ownership

The boundaries are meant to keep finance logic auditable and prevent frontend or worker code from quietly owning data it should not own.

Core API

Primary product system

Owns users, drivers, trucks, trips, costs, refuels, tolls, reserves, receivables, documents, compliance metadata, authentication, validation, and persistence. Implementation should keep explicit internal modules for profile, trip, finance, reserve, compliance, receivables, and imports.

Finance Worker

Auditable calculations

Owns trip profitability, reserve allocation, safe withdrawal, fuel estimates, waiting-time impact, customer profitability, financial health, and idempotent event handling.

Data Importer

External datasets

Owns ANP diesel imports, future ANTT toll and freight-floor imports, import audit records, freshness status, retries, and failure reporting.

Mobile App

Driver workflows

Owns mobile navigation, validation presentation, offline and error states, and API client usage. It should not become the source of business math.

Web App

Admin and support

Owns admin/backoffice workflows, demo visibility, support screens, and operational dashboards when enabled.

Docs

Markdown remains canonical

APIs And Events

The API contracts explain what client and backend calls should exist. Event contracts explain how the Core API asks workers to do asynchronous work.

HTTP APIs

Driver-facing product actions

Planned endpoints cover profile and tax setup, trips, profitability estimates, expenses, reserves, fuel prices, tolls, Vale-Pedagio, compliance, customers, and receivables.

Response shape

Results need traceability

Profitability responses must include gross freight, direct cost, required reserves, safe personal withdrawal, financial health, currency, and a calculation trace ID.

RabbitMQ events

Async domain work

Canonical events include trip.recalculation.requested, trip.finance.recalculated, reserve.allocation.requested, and import completion events.

Event rules

Reliable and auditable

Events need versions, event IDs, correlation IDs, action timestamps, idempotent consumers, decimal-string monetary values, and no secrets or raw document content.

Data Model

The model is organized around identities, trucks, trip economics, reserves, Brazil-specific datasets, compliance, receivables, and import audits.

Identity

Who and what is operating

Users, drivers, companies, trucks, trailers, tax profiles, yearly tax rules, and IPVA rules define the operating profile.

Trip economics

How a freight becomes a decision

Freights, trips, expenses, refuels, cost inputs, profitability snapshots, freight-floor checks, waiting time, and consumption profiles explain the money.

Reserves

Money set aside

Reserve buckets, transactions, and rules separate maintenance, tires, taxes, insurance, replacement, emergency, salary, and profit decisions.

Brazil data

External operating facts

Fuel prices, station prices, driver fuel reports, toll plazas, tariffs, trip tolls, and Vale-Pedagio records support localized decisions.

Compliance

Advisory records

RNTRC, insurance, compliance documents, alerts, score snapshots, maintenance, and tire records keep operational risks visible.

Audit

Explainability by default

Financial, import, compliance, and document records should keep timestamps and enough input metadata to explain how a value was produced.

Auth, Security, And Observability

These docs set the operating rules for user access, sensitive data, logs, health checks, tracing, import freshness, and finance calculation visibility.

Auth

Separate from official portals

Cofrete app login is separate from gov.br, ANTT, RNTRC Digital, Receita Federal, ANP, SUSEP, insurers, and state systems.

Security

Sensitive trucking data

The platform may handle CPF/CNPJ metadata, plates, RENAVAM, RNTRC, insurance documents, receipts, freight values, customer payment history, and future location data.

Observability

Signals that matter

Services should expose health/readiness, structured logs, correlation IDs, import audit records, calculation traces, retry and dead-letter visibility, and dataset freshness indicators.

Deployment And Kubernetes

Deployment docs make one thing explicit: Docker Compose is for local development, while production is intended to run on the user's Kubernetes cluster.

1

Local

Docker Compose is planned as a developer convenience for PostgreSQL, RabbitMQ, MinIO, and service networking once those files exist.

2

CI

GitHub Actions should run the repository harness, service tests, image build validation, and future manifest validation.

3

Staging

The staging namespace should validate release candidates with production-like configuration before promotion.

4

Production

Core API, workers, and web admin should run as Kubernetes workloads. Stateful dependencies need explicit backup, restore, durability, and ownership decisions.

Pending discovery

Cluster facts are not confirmed

No real namespaces, ingress classes, storage classes, operators, registry credentials, certificate issuers, or observability components have been confirmed from this workspace.

Proposed defaults

Use until discovery succeeds

Proposed namespaces are cofrete-staging and cofrete. Images should use immutable Git SHA tags, and workers should not be externally exposed.

Design Rules To Preserve

These rules show up across the architecture docs and should guide future code, schemas, infrastructure, and tests.

Finance

Deterministic and auditable

Financial calculations must be repeatable, traceable, and backed by input/output snapshots.

Modularity

Core API starts modular

The first Core API implementation should separate profile, trip, finance, reserve, compliance, receivables, and imports so domains can be tested independently and extracted later.

Imports

Server-side official data

External ANP and ANTT datasets should be imported by backend services, not fetched directly from clients.

Compliance

Advisory wording only

Cofrete should link to official sources and avoid presenting itself as a government, legal, tax, accounting, or insurance channel.

Traceability

Correlation IDs everywhere

API requests, events, logs, calculation traces, and import records should be connected by identifiers.

Secrets

Never commit secret values

ConfigMaps may hold non-secret settings. Credentials belong in Kubernetes Secrets or the cluster's secret-management convention.

Operations

Backups before production

Production data is not ready without documented backup schedules, restore tests, queue durability, and object-storage retention.
