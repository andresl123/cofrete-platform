ROU-217 / COF-013 Reserve Bucket And Safe Withdrawal

This manually maintained derived explainer summarizes the ROU-217 / COF-013 implementation. Canonical product and contract wording remains in the Markdown docs under docs/.

What Changed

  • Core API now persists reserve rules, reserve wallets, reserve allocations, and reserve transactions.
  • Core API exposes POST /api/reserve-rules, GET /api/reserve-wallets, POST /api/reserve-allocations, and GET /api/financial-health-score.
  • Reserve wallet responses include recent transaction history so mobile can render an auditable ledger.
  • Finance Worker now has deterministic reserve allocation logic and handles reserve.allocation.requested through an idempotent service.
  • Core API is documented as the temporary synchronous reserve allocation owner for ROU-217; ROU-253 owns the final async worker result persistence path.
  • Duplicate idempotency calls are reported in response metadata without changing the stored allocation status.
  • ROU-217 manual corrections are positive credit allocations only; debit and adjustment corrections require a later contract.

Why

ROU-217 / COF-013 builds on the deterministic finance engine by allocating freight payment money into virtual reserve buckets and keeping pass-through cash flow out of safe personal withdrawal.

Caveats

Reserve allocations are virtual ledger movements. They are advisory planning output, not real money movement and not legal, tax, accounting, insurance, or government guidance.
